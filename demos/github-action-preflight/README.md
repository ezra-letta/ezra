# Read-only Letta GitHub Action preflight

This zero-dependency diagnostic checks whether a repository is ready for the
Letta Code GitHub Action setup flow. It does not create branches, set secrets,
edit workflows, call the Letta API, or print GitHub tokens.

It checks:

- whether the current directory is a Git repository with a GitHub `origin`
- whether GitHub CLI (`gh`) is installed and authenticated
- whether visible classic-token scopes include `repo` and `workflow`
- whether a standard Letta workflow exists
- whether that workflow uses the current action, secret references,
  write permissions, and issue-comment trigger generated by Letta Code

## Run it

```bash
git clone https://github.com/ezra-letta/ezra.git
cd ezra/demos/github-action-preflight
npm test
node preflight.mjs /path/to/your/repository
```

For machine-readable output:

```bash
node preflight.mjs --json /path/to/your/repository
```

Exit code `0` means no blocking failure was found. A missing workflow is a
warning because the repository may simply not be configured yet. Other failed
checks return exit code `1`.

## Expected output

Against an authenticated GitHub repository that has not installed the action:

```text
Letta GitHub Action preflight
Repository: owner/repo

[OK] GitHub origin: owner/repo
[OK] GitHub token scopes: repo and workflow scopes are present
[WARN] Letta workflow: No standard workflow found. In Letta Code, run /install-github-app to create a reviewed setup PR.

No blocking preflight failures found. Review the workflow before merging.
```

## What happens next

Run this inside the target repository in an interactive Letta Code session:

```text
/install-github-app
```

The built-in setup flow performs the mutating work: it checks repository
access, creates a branch, writes the workflow, configures `LETTA_API_KEY` and
an optional agent variable, commits the change, and opens a setup pull request.
Review that pull request before merging it. `@letta-code` mentions do not work
until the workflow reaches the default branch.

## Boundaries

- This is a static preflight, not a security audit or proof that a workflow
  run will succeed.
- Fine-grained GitHub tokens may not expose classic scope text. When `gh` omits
  scopes, the report asks you to verify repository/workflow access manually.
- The workflow analysis intentionally avoids a YAML dependency. It validates
  the contract generated by current Letta Code and may flag heavily refactored
  but valid custom workflows.
- The script never runs `gh secret list`; secret names can reveal project
  configuration. It verifies only that the workflow references the expected
  GitHub secret expressions.
